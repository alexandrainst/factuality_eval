What "Ground Truth" Means Here

The repo uses the phrase in several related but different ways.

Reference answer

QA answer correctness

The original answer from MultiWikiQA is used as the reference answer when generated model answers are graded in ground_truth.py and displayed in manual_check.py.

Token/span label

Hallucination detector truth

Synthetic MultiWikiQA and RAGTruth provide character spans or token-aligned labels for hallucinated answer text. These labels are used to train and evaluate the token classifier.

Review verdict

LLM and human checks

ground_truth_eval.py builds a review dataset with detector predictions, LLM verdict slots, and human annotation slots so reviewers can compare model, LLM, and human judgments.

Validation, Verification, and Ground Truth

Use the tabs to switch between the major validation layers.

LLM grading against gold answers

src/scripts/ground_truth.py generates answers from config.models.eval_model, compares each generated answer with the original dataset answer, and asks gpt-4o-mini for a one-word verdict.

  • English uses yes/no; Danish, German, Icelandic, and Faroese use language-specific positive tokens such as ja.
  • The prompt counts explicit containment, clear statement, or partial overlap with the ground truth as correct.
  • Results are written to data/ground_truth/<model>_<language>_results.json.

Manual check report

manual_check.py builds a Markdown table with question, ground truth, generated answer, and empty verdict/notes columns.

  • Ground truth is looked up by (context[0], question).
  • The config target is data/ground_truth/manual_check_da_Qwen3-0.6B.md.
  • It is useful as a lightweight human audit path, but it does not compute metrics by itself.

Synthetic MultiWikiQA labels

dataset_generation.py samples hallucination intensities from a clipped Beta distribution, calls LettuceDetect's hallucination generator, and converts returned hallucinated parts into character spans.

  • Each QA pair becomes a faithful example with empty labels and a hallucinated example with hallucinated_labels.
  • Ambiguous hallucinated parts are discarded if a part is absent from the answer or appears more than once.
  • Overlapping spans are filtered so longer accepted spans take priority.

Detector evaluation on labels

evaluate_ground_truth.py loads the hub synthetic-hallucinations dataset and evaluates the trained token classifier with LettuceDetect's evaluate_model.

  • It splits the loaded train set with test_size=0.2, seed=42, and shuffle=False.
  • It formats rows to the LettuceDetect/RAGTruth sample schema before token classification.
  • Metrics include token-level precision, recall, F1, and AUROC through LettuceDetect.

Ground-truth evaluation dataset

build_ground_truth_evaluation_dataset writes one JSONL row per generated answer with detector tokens, concatenated predicted hallucinated text, and placeholders for LLM and human annotation.

  • Output: data/final/ground_truth_evaluation_dataset.jsonl.
  • Detector fields: tokens and model_predicted_hallucinated_text.
  • Review fields: llm_hallucinated_parts, llm_explanation, human_annotation_labels, and human_annotation_notes.

LLM span verdict pass

llm_evaluate_ground_truth.py fills the LLM columns by asking the configured model to return JSON with exact hallucinated substrings and an explanation.

  • The pass is idempotent: rows with non-empty llm_explanation are skipped.
  • It atomically checkpoints every 25 API calls.
  • The prompt asks for answer spans unsupported by, or contradictory to, the context.

Hand/LLM-annotated detector diagnosis

analysis/diagnose_detector.py operates on the first 260 rows of data/final/ground_truth_evaluation_dataset.jsonl with populated llm_hallucinated_parts.

  • It converts hallucinated substrings to a character mask, then aligns detector tokens to that mask.
  • It computes confusion matrices, threshold sweeps, token category breakdowns, stratified metrics, and cheap post-processing rules.
  • Outputs are detector_diagnosis.md, detector_diagnosis_findings.md, and detector_diagnosis.json.

Main diagnostic conclusion

The analysis says cheap post-hoc rules recover only about one token-F1 point. The dominant problem is structural: high-confidence false positives and weak recall on entity mis-attribution inside context.

  • Best threshold by F1: 0.60, only lifting token F1 from 0.303 to about 0.310.
  • Strongest category: invented numbers not in context.
  • Weakest important category: entities that appear in context but are assigned incorrectly.

Preprocessed and translated labels

preprocess_ragtruth.py converts RAGTruth response.jsonl and source_info.jsonl into LettuceDetect HallucinationSample objects.

  • Each RAGTruth label becomes a span with start, end, and label_type.
  • translate.py preserves hallucination spans across translation by inserting <HAL> tags before translation and recovering spans afterward.
  • The current config points to data/processed/ragtruth_da/ragtruth_data_da.json.

Training mix

train_hallucination_detector.py can combine synthetic MultiWikiQA and translated RAGTruth data according to config.ragtruth.enable and config.multiwikiqa.enable.

  • The Danish config enables both sources.
  • RAGTruth's native train and test splits are respected.
  • Combined train/test datasets are shuffled after splitting to interleave sources.

A

Generation and label extraction

Synthetic data is generated by generate_dataset.py and dataset_generation.py. Each accepted hallucinated part is converted to a character span in the answer. The system rejects ambiguous spans that cannot be mapped reliably.

B

Detector training and test split

train_hallucination_detector.py loads synthetic hub data and/or translated RAGTruth, converts it to the RAGTruth/LettuceDetect format, and trains or evaluates the token classifier.

C

Generated answer evaluation

detect_hallucinations.py and phase 2 of evaluate_ground_truth.py run the detector on generated answers, reporting token hallucination rate and rate of answers with at least one flagged token.

D

Reviewer-facing dataset

Phase 3 of evaluate_ground_truth.py builds ground_truth_evaluation_dataset.jsonl, which lets detector predictions, LLM verdicts, and future human annotations be compared on the same rows.

Key Findings

What the existing validation reveals.

What works

  • The repo has a real token-level validation path through synthetic/RAGTruth labels and LettuceDetect metrics.
  • The LLM/human review dataset is practical: each row keeps context, question, answer, detector tokens, LLM verdicts, and human slots together.
  • Generation label extraction includes safeguards against missing, duplicated, or overlapping hallucinated parts.
  • The diagnosis script goes beyond aggregate F1 by doing threshold sweeps, category analysis, and post-processing experiments.

What the results say

  • Post-processing has a low ceiling: token F1 moves from 0.303 to only about 0.310.
  • High-confidence false positives are a model problem, not just a bad threshold.
  • The detector is better at invented out-of-context numbers than at wrong entity-fact assignments.
  • Question-token filtering helps precision, while context-token whitelisting hurts recall because hallucinations often reuse context words incorrectly.

Risks and Gaps

Important caveats in the current ground truth strategy.

Concept drift

Ground truth types are mixed

Reference answer correctness, hallucinated span labels, and LLM/human span verdicts are different targets. The repo currently uses similar naming for all of them, which can make metrics easy to misread.

LLM as judge

LLM verdicts need calibration

ground_truth.py asks for a binary yes/no answer with permissive partial-overlap criteria. llm_evaluate_ground_truth.py asks for exact spans. These are useful but not equivalent to human adjudication.

Alignment

Substring matching can be brittle

The diagnosis maps llm_hallucinated_parts into character masks by substring search. Repeated substrings, whitespace differences, and tokenization quirks can produce noisy token-level truth.

Data split

Synthetic split is deterministic but not shuffled

evaluate_ground_truth.py uses shuffle=False in the synthetic train/test split. If the hub dataset has ordering artifacts, the test split may not represent the full data distribution.

Translation

Translated RAGTruth needs QA

The translation workflow preserves <HAL> tags, but logs show earlier API-key failures and the translated file is large enough that systematic span-preservation validation is important.

Artifacts

Experiment outputs are absent locally

No files were found under outputs/ or multirun/ in this workspace, so this report relies on source code, analysis/, config, and data files rather than Hydra run logs.

Recommended Improvements

Prioritized changes to make validation stronger and easier to trust.

1. Separate evaluation targets explicitly

Rename/report metrics by target: answer_correctness, span_hallucination_detection, and review_adjudication. This will prevent binary answer grading from being confused with token-level hallucination scoring.

2. Add an adjudicated human set

Fill human_annotation_labels for a fixed validation subset, use at least two annotators where possible, and track agreement. Keep LLM verdicts as assistance, not final truth.

3. Improve span alignment

Store explicit character offsets for LLM/human hallucinated spans instead of only substrings. If substrings are kept, store occurrence indices and normalized text checks to avoid repeated-substring ambiguity.

4. Add entity-misattribution training data

The diagnosis identifies entity-in-context mis-attribution as the largest gap. Generate targeted examples where facts from the context are assigned to the wrong person, place, date, or organization.

5. Evaluate by source and language

Report metrics separately for synthetic MultiWikiQA, translated RAGTruth, and each language. This will show whether failures come from synthetic generation, translation noise, domain mismatch, or model limits.

6. Calibrate detector probabilities

Because false positives and true positives both have high probabilities, add calibration plots and metrics such as ECE/Brier score. Consider loss reweighting, stronger encoders, and span-level objectives.

7. Make run artifacts reproducible

Persist the exact Hydra config, dataset revision, model revision, split seed, threshold, and commit SHA beside every report. Link these from future HTML or Markdown reports.

8. Add CI checks for label integrity

Test that hallucinated labels are inside answer bounds, non-overlapping after normalization, reconstructable from substrings, and preserved after RAGTruth translation.
